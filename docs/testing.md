# Тестирование и измерение нагрузки

## Уровни проверок

1. Модульные тесты: денежная точность, округление, валидация, повторы запроса, конфликты ключей, расчёт и освобождение резерва, классификация ответов шлюза.
2. Интеграционные тесты PostgreSQL: миграции, уникальные ограничения, конкурентные списания и повторы, атомарность outbox, восстановление обработки, конечные остатки.
3. Сквозной сценарий с PostgreSQL, RabbitMQ, Celery, outbox и тестовым шлюзом: принятый HTTP-запрос должен дойти до конечного результата, а повтор не должен создать вторую операцию.
4. Нагрузочный прогон: скорость приёма, скорость завершения, задержки, возраст очереди и инварианты денег при заданных ресурсах.

Прохождение модульных тестов не доказывает корректность конкурентных транзакций или надёжность полного пути через брокер.

## Локальные команды

```bash
poetry install
poetry run pytest -q -m "not integration"
poetry run ruff check .
```

Интеграционные проверки требуют `TEST_DATABASE_URL`, указывающий на отдельную мигрированную БД с именем, оканчивающимся на `_test`. Перед каждым тестом её таблицы очищаются. Не используйте рабочую БД.

Пример для локальных значений из `.env.example`, Bash:

```bash
docker compose up -d db
docker compose exec db createdb -U payments payments_test
export TEST_DATABASE_URL='postgresql+asyncpg://payments:payments-local@127.0.0.1:15432/payments_test'
DATABASE_URL="$TEST_DATABASE_URL" poetry run alembic upgrade head
poetry run pytest -q -m integration
```

Если БД `payments_test` уже создана, пропустите `createdb`. При изменённых портах или паролях используйте соответствующий URL. Без `TEST_DATABASE_URL` интеграционные проверки пропускаются, а не считаются пройденными. В PowerShell переменные задаются через `$env:TEST_DATABASE_URL` и `$env:DATABASE_URL`.

Для проверки цепочки миграций создайте ещё одну отдельную БД. Эти тесты пересоздают её схему и проверяют upgrade/downgrade, сохранение старых задач и отказ при неконсистентных данных:

```bash
docker compose exec db createdb -U payments payments_migrations_test
export TEST_MIGRATION_DATABASE_URL='postgresql+asyncpg://payments:payments-local@127.0.0.1:15432/payments_migrations_test'
poetry run pytest -q -m integration
```

Эта БД должна отличаться от `TEST_DATABASE_URL` и тоже иметь суффикс `_test`. Без явного URL проверки миграций пропускаются.

Для ручного сквозного сценария:

```bash
docker compose --profile dev up --build -d
curl --fail http://127.0.0.1:18080/ready
```

Создайте пользователя, отправьте списание с уникальным `Idempotency-Key`, дождитесь `success`, повторите тот же запрос и проверьте тот же `payment_id`. Измените сумму с тем же ключом и проверьте конфликт. Затем отправьте несколько конкурирующих списаний, сумма которых превышает доступный остаток: принятые резервы не должны превышать баланс.

## Восстановление после сбоев

В отдельном тестовом окружении проверьте следующие окна отказа:

| Сбой | Проверяемое поведение |
|---|---|
| Брокер недоступен после фиксации платежа | Outbox остаётся и доставляет задачу после восстановления |
| Relay упал после публикации до фиксации результата | Повторная публикация не повторяет изменение баланса |
| Worker прерван до запроса к провайдеру | Задача возобновляется после истечения аренды |
| Ответ потерян после обработки у провайдера | Повтор использует тот же ключ; неизвестный результат удерживает резерв |
| Два worker одновременно получили один платёж | Применяется только допустимый результат владельца аренды |
| Повтор окончательно завершённого платежа | Баланс и транзакция повторно не меняются |

Не создавайте искусственные отказы в работающем платёжном окружении.

## Ограниченный сквозной прогон

`scripts/load_test.py` создаёт новые тестовые счета, отправляет пополнения по `1.00`, повторяет часть запросов с тем же ключом, ждёт конечных состояний и проверяет остатки через `GET /api/v1/users/{id}`. Скрипт не очищает созданные данные. Используйте отдельный одноразовый экземпляр с тестовым шлюзом.

Пример для Bash после запуска dev-окружения:

```bash
export API_KEY='your-local-service-key'
poetry run python scripts/load_test.py \
  --base-url http://127.0.0.1:18080 \
  --requests 100 --accounts 10 --concurrency 10 --timeout 120 \
  --output load-results-local.json
```

В PowerShell задайте `$env:API_KEY` перед той же командой; параметры можно передать одной строкой. Значение ключа должно совпадать с API_KEY работающего экземпляра. По умолчанию разрешён только localhost; `--allow-remote` требует осознанно выбранного отдельного тестового адреса.

В отчёте отдельно указаны принятые и успешно завершённые платежи в секунду, p50/p95/p99 времени платёжного HTTP-запроса, ошибки, незавершённые платежи и ошибки сверки остатков. Задержки запроса относятся к принятию, а не ко времени окончательной обработки у провайдера. Дедлайн `--timeout` отсчитывается от начала подачи запросов. При ошибках или незавершённых платежах скрипт возвращает ненулевой код.

Это ограниченная сквозная проверка, а не готовая характеристика максимально возможной нагрузки. Для поиска предела увеличивайте поток и длительность постепенно, наблюдая ресурсы и возраст очереди, и сохраняйте параметры каждого прогона. Внешний провайдер и реальные сетевые задержки требуют отдельных согласованных испытаний.
## Нагрузка

Используйте отдельный набор пользователей и уникальные ключи запросов. Тестовый шлюз проверяет поведение приложения, но не воспроизводит лимиты, задержки и доступность реального провайдера.

Записывайте вместе с результатами:

- commit SHA и image digest;
- CPU, память, диск и сеть;
- количество реплик API, воркеров, конкуренцию и размеры пулов БД;
- число пользователей, долю горячих счетов, операции и суммы;
- задержки/ошибки провайдера и выбранные лимиты повторов;
- длительность разогрева и основного прогона;
- принятые запросы в секунду и окончательно завершённые платежи в секунду;
- p50/p95/p99, ошибки, возраст очереди, резерв и итоговую сверку денег.

Заявление о выдерживаемой нагрузке относится только к измеренному сценарию и ресурсам. HTTP-ответ о принятии задачи не считается завершённым платежом. После прекращения подачи нагрузки очередь должна опустеть либо содержать только объяснимые операции ручного разбора.
