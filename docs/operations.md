# Эксплуатация

## Подготовка окружения

Production-развёртывание использует `docker-compose.yml` вместе с `compose.production.yml`. Нужны Docker Compose 2.24.4+, внешний TLS reverse proxy и провайдер, соответствующий [контракту шлюза](api.md).

До запуска задайте в защищённом `.env`:

| Переменная | Назначение |
|---|---|
| `APP_ENV=production` | Строгая проверка настроек |
| `DEBUG=false` | Отключение отладочного режима |
| `PAYMENTS_IMAGE` | Проверенный неизменяемый тег или digest образа |
| `API_KEY` | Уникальный сервисный ключ, минимум 32 символа |
| `POSTGRES_PASSWORD` | Собственный пароль PostgreSQL |
| `RABBITMQ_PASSWORD` | Собственный пароль RabbitMQ |
| `DOCKER_DATABASE_URL` | URL PostgreSQL внутри сети контейнеров |
| `DOCKER_CELERY_BROKER_URL` | URL RabbitMQ внутри сети контейнеров |
| `PAYMENT_GATEWAY_URL` | Адрес реального провайдера |
| `GATEWAY_API_KEY` | Секрет провайдера, если требуется его контрактом |
| `GATEWAY_IDEMPOTENCY_NAMESPACE` | Постоянное уникальное пространство ключей этого окружения |

URL должны соответствовать `POSTGRES_USER`, `POSTGRES_DB` и `RABBITMQ_USER`. Спецсимволы паролей внутри URI кодируются percent-encoding. Учётные данные не включаются в Docker image и не публикуются в логах или репозитории. Ограничьте права доступа к `.env` и резервным копиям.

Для каждого окружения установите собственный постоянный `GATEWAY_IDEMPOTENCY_NAMESPACE`, например `payments-production-01`. Не используйте локальный пример `payments-local` или одно пространство для независимых БД, работающих с одним провайдером. Изменение пространства для уже принятых платежей может превратить повтор в новое списание.

Один общий сервисный ключ предполагает доверенную серверную интеграцию. Для нескольких независимых клиентов нужно добавить отдельную идентификацию/авторизацию клиентов, область действия ключей и ограничения доступа к счетам до публикации API для них.

## Образ и миграции

Образ содержит только runtime-зависимости и код приложения. Он запускается пользователем с UID 10001; файловая система контейнера приложения доступна только для чтения, временные файлы находятся в `/tmp`.

Пример сборки на сервере или подготовленной сборочной машине:

```bash
docker build --target runtime -t payments:release-2.0.0 .
```

Присвойте выпуску собственный уникальный тег, например `payments:release-2.0.0`, и установите `PAYMENTS_IMAGE` в `.env`. Для нескольких выпусков в день добавьте номер сборки или commit SHA. При использовании реестра предпочтителен digest: `registry.example/payments@sha256:...`. Теги базовых PostgreSQL/RabbitMQ фиксируют основную версию, но не являются immutable digest; обновления инфраструктуры требуют отдельной проверки и резервной копии.

Проверка конфигурации без вывода секретов:

```bash
docker compose -f docker-compose.yml -f compose.production.yml config --quiet
```

Последовательность первого запуска:

```bash
docker compose -f docker-compose.yml -f compose.production.yml up -d db rabbitmq
docker compose -f docker-compose.yml -f compose.production.yml run --rm migrate
docker compose -f docker-compose.yml -f compose.production.yml up -d --no-build api worker outbox
curl --fail http://127.0.0.1:18080/ready
```

На сервере с TLS reverse proxy направьте запросы на `127.0.0.1:${API_PORT}`. В production-конфигурации PostgreSQL и RabbitMQ не публикуют порты хоста. Не включайте профиль `dev` в production: тестовый шлюз предназначен для проверок.

Перед обновлением сохраните проверенный backup и предыдущий image digest. Остановите приём запросов и обработчики, если новая миграция несовместима с предыдущим кодом. Примените миграции одним отдельным процессом, затем поднимите совместимую версию приложения. Для совместимых схем можно обновлять реплики постепенно; это требует отдельного reverse proxy/оркестратора и проверки готовности.

Если обновляется старая БД с незавершёнными платежами, сначала сверяйте их с провайдером и проверяйте резервы. Унаследованные операции без подтверждённой истории резервирования переводятся в ручной разбор; обычная команда сверки не исправляет их учёт автоматически.

Не выполняйте слепое `alembic downgrade` на рабочей БД. Откат образа допустим только при совместимой схеме; иначе требуется проверенная обратная миграция или восстановление в отдельную БД. Изменение уже применённых миграций не заменяет новую миграцию.

## Диагностика

```bash
docker compose ps
docker compose logs --tail=200 api worker outbox
docker compose exec api alembic current
```

`/health` проверяет процесс. `/ready` проверяет БД и брокер; успешный readiness не подтверждает доступность реального провайдера и не гарантирует, что worker/outbox успевают обрабатывать очередь.

`/metrics` защищён сервисным ключом. Настройте Prometheus передавать `X-API-Key` и опрашивать каждый экземпляр API. Счётчики HTTP относятся к экземпляру процесса, а состояние платежей, резервов и outbox считывается из PostgreSQL. Для общих DB-показателей используйте одну выбранную реплику или агрегацию `max`, а не сумму одинакового состояния всех API.

Параметры таймаутов согласуются между собой: `CELERY_TASK_SOFT_TIME_LIMIT_SECONDS < CELERY_TASK_TIME_LIMIT_SECONDS < WORKER_PROCESSING_TIMEOUT_SECONDS`, а аренда обработки также должна быть длиннее `GATEWAY_TIMEOUT_SECONDS`. Настройки проверяются при старте. Слишком короткая аренда увеличивает параллельные повторы; слишком длинная замедляет восстановление после остановки worker.

Наблюдайте отдельно:

- частоту ошибок и задержки HTTP;
- количество принятых и завершённых платежей;
- старейшие ожидающие записи outbox и рост очереди;
- зависшие обработки и операции `reconciliation_required`;
- DLQ и окончательные отказы провайдера;
- резерв средств и инвариант `0 <= reserved_balance <= balance`;
- соединения БД, блокировки, диск, память и состояние RabbitMQ.

Пороги задержек и возраста очереди выбираются по требованиям вашего продукта. Не скрывайте рост очереди за высоким HTTP RPS.

## Неопределённый результат провайдера

1. Найдите платёж по идентификатору и проверьте его состояние.
2. Запросите у провайдера результат по исходному стабильному ключу идемпотентности.
3. Сохраните ссылку или идентификатор подтверждения провайдера.
4. Примените только подтверждённый итог операционной командой.

Команды выполняются с теми же production-настройками, что и приложение. Сначала проверьте состояние:

```bash
docker compose exec api python -m app.operations inspect --payment-id 123
```

После проверки результата у провайдера, для подтверждённого успеха:

```bash
docker compose exec api python -m app.operations reconcile \
  --payment-id 123 --outcome success \
  --reference provider-receipt-123 --confirm-provider-outcome
```

Для подтверждённого отказа используется `--outcome failed`. `--reference` — реальный идентификатор квитанции провайдера или карточки сверки. Флаг подтверждения означает, что оператор уже проверил исход; команда сама не запрашивает провайдера и не выполняет повторное списание. Результат с ссылкой фиксируется в аудите `payment_resolutions`. Команда предназначена только для состояния `reconciliation_required`; конфликтующее повторное решение отклоняется.

Унаследованные операции с `legacy_payment_requires_reconciliation` требуют отдельного восстановления учёта: обычная команда не создаёт вымышленные резервы и не применяет к ним исход автоматически. Старые записи задач сохраняются в `legacy_payment_tasks`. Обратная миграция запрещается при наличии записей outbox, квитанций провайдера или результатов сверки, чтобы не уничтожить эти свидетельства.

Для проверки аргументов используйте `docker compose exec api python -m app.operations --help`. Не передавайте токен провайдера через аргументы командной строки.

Не удаляйте платёж и запись outbox для повторного списания. Не снимайте резерв по одному факту истечения HTTP-таймаута. Если провайдер не может подтвердить исход, операция остаётся на ручном разборе.

## Backup и восстановление

В каталоге проекта, Python 3.12:

```bash
python scripts/backup.py --project payments
```

Скрипт делает PostgreSQL dump в custom format, не перезаписывает существующий файл и создаёт SHA256. Переносите копии в отдельное защищённое хранилище, проверяйте срок хранения и регулярно выполняйте тестовое восстановление. Backup не является проверенным, пока он не восстановлен и данные не сверены.

Восстановление в **новую** БД:

```bash
python scripts/restore.py backups/payments-YYYYMMDDTHHMMSSZ.dump --database payments_restore --project payments
```

Скрипт откажется использовать существующую БД. Затем проверьте схему, миграции, количество платежей и транзакций, остатки и резервы. Для подключения приложения к восстановленной БД потребуется изменить `DATABASE_URL`/`DOCKER_DATABASE_URL` после проверки. На время переключения остановите приём новых запросов и обработку старого окружения.

Эти скрипты делают логическую копию PostgreSQL. Для требований к малой потере данных и восстановлению на момент времени настройте PostgreSQL WAL/PITR и проверьте соответствующий runbook. Резервная копия RabbitMQ не заменяет БД и outbox как источники состояния платежа.

Перед возобновлением платежей после восстановления сверяйте операции у провайдера за период после backup. Внешние списания могли сохраниться, даже если их записей больше нет в восстановленной БД. Проверьте последовательности идентификаторов и старые ключи провайдера, чтобы новый платёж не переиспользовал ключ уже выполненного. Не меняйте namespace для обхода конфликта: это может повторить списание. Порядок сверки зависит от контракта провайдера.

Обычная остановка сервиса сохраняет данные:

```bash
docker compose down
```

Не удаляйте volumes для исправления миграций или ошибок приложения.
